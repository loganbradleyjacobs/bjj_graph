- finalize data storage method
/goal The goal is to finalize the data storage method used for this project. I currently use one moveset.json file to list all of the moves. I render this in a graph, with nodes and edges, where the positions are the nodes, and the edges would be the moves, if they were named, which they are currently not. The edges are generated from the parent to the child. This might even be a misnomer though, as I want the edges to be bidirectional, like they are rendered. Should I use an adjacency graph or an adjacency list, keep the json representation, or go to a nosql database?

- finalize data structure
I want to revisit how we are representing the data. My qualm with storing submissions as edges is that they are not simple moves, they often have smaller details that need to be adjusted for the submission to work, and I want to represent my knowledge of those too. I am okay with storing a md file or imgs/video links along with the node to walk me through this, but I don't want to do all that for edges. Submissions should be a leaf node, and often are in my graph, I just noticed for example, Clock Choke is a self-loop, but also Clock Choke from Back is a submission node, so I wanted to be clear on that.

/goal I want to store the x and y coordinates for each node, and edge, such that I can move them around and return to that view after refreshing. I don't want to store area anymore. I do like the "type" attribute, but I want to refactor the type to only include the following ones: "Pin" (currently called control), "Submission", "Pass", "Guard", and Custom, which will be able to be entered manually. I may adjust this list later, but this is a good preliminary list.
